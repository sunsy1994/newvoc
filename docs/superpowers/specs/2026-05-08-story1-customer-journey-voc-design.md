# 故事线2：VOC看用户的渠道级旅程系统

## 1. 产品定位

“VOC看用户”不是跨渠道追踪某一个真实用户，而是把不同渠道中的用户声音统一映射到汽车业务旅程阶段，帮助业务看清：

- 每个阶段用户在问什么、担心什么、吐槽什么。
- 哪些渠道主要承载哪些阶段的声音。
- 用户从兴趣到留资、从报价到下订/战败、从到店到售后的阻碍在哪里。
- 哪些问题应该由市场、销售、DCC、门店、售后分别处理。

首期必须坚持一个边界：

**不做跨渠道用户打通。**

原因是 400、企业微信、DCC、公网平台、大众点评多数没有可安全打通的统一用户ID。首期只做“渠道级用户旅程阶段归因”，不把不同渠道中的昵称或号码推断成同一个人。

## 2. 核心模式

产品采用混合模式：

1. **VOC用户阶段信号**
   - 来源：抖音、快手、小红书等公网帖子和评论。
   - 作用：识别用户公开表达处在哪个阶段，例如曝光认知、兴趣咨询、对比评估、价格咨询、售后表达。

2. **真实业务触点阶段**
   - 来源：400、企业微信、DCC、大众点评店铺数据。
   - 作用：提供更强业务语义的触点阶段，例如留资、外呼、邀约、到店、报价、战败、门店体验、售后反馈。

两层数据统一进入一张“触点表”，再按旅程阶段汇总。

## 3. 旅程阶段

首期采用一条业务可落地的阶段链：

`曝光认知 -> 兴趣咨询 -> 对比评估 -> 留资/外呼 -> 试驾/到店 -> 报价/权益 -> 下订/战败 -> 交付/售后 -> 复购/推荐`

阶段定义如下：

| 阶段 | 含义 | 典型表达或业务信号 |
| --- | --- | --- |
| 曝光认知 | 用户知道品牌/车型/活动 | 刷到、看见发布、第一次听说 |
| 兴趣咨询 | 用户开始问基础信息 | 多少钱、什么时候上市、哪里看车、配置是什么 |
| 对比评估 | 用户把本品与竞品/需求比较 | 和竞品比、值不值、续航/空间/配置比较 |
| 留资/外呼 | 用户已留下线索或进入电话触达 | DCC线索、400咨询、外呼记录 |
| 试驾/到店 | 用户出现试驾或到店体验 | 想试驾、预约、到店、销售接待 |
| 报价/权益 | 用户进入价格、金融、权益谈判 | 报价、优惠、金融方案、置换、保险 |
| 下订/战败 | 用户表达成交或放弃 | 已订、退订、等优惠、买竞品、放弃 |
| 交付/售后 | 用户进入提车、用车、维修服务 | 提车、交付、维修、售后、投诉、保养 |
| 复购/推荐 | 用户表达推荐、转介绍或复购 | 推荐朋友、还会买、家里第二台 |

## 4. 渠道阶段映射

| 渠道 | 首期可归因阶段 | 归因方式 |
| --- | --- | --- |
| 抖音/快手/小红书等公网 | 曝光认知、兴趣咨询、对比评估、报价/权益、交付/售后 | 文本标签优先，渠道默认阶段辅助 |
| 400 | 兴趣咨询、留资/外呼、交付/售后 | 来电摘要、工单类型、咨询/投诉标签 |
| 企业微信 | 留资/外呼、试驾/到店、报价/权益、下订/战败、交付/售后 | 会话文本和跟进状态 |
| DCC | 留资/外呼、试驾/到店、报价/权益、下订/战败 | 线索阶段、外呼结果、邀约/到店/战败字段 |
| 大众点评店铺 | 试驾/到店、报价/权益、交付/售后、复购/推荐 | 店铺评价、评分、门店/服务关键词 |

如果渠道默认阶段与文本标签冲突，优先使用文本或业务字段。例如大众点评评价默认更接近到店/服务，但如果文本明确是“提车后首保”，则归入交付/售后。

## 5. 首期页面

### 5.1 用户旅程总览

横向展示九个阶段，每个阶段只展示可由底表或ETL支撑的指标：

- 触点数
- 渠道数
- 负向占比
- Top问题
- Top意图
- 代表原声
- 数据来源渠道

不展示“阶段转化率”，因为首期没有跨渠道用户ID，不能证明同一用户从一个阶段流到下一个阶段。

### 5.2 阶段详情

选中某个阶段后，展示：

- 该阶段渠道分布
- 该阶段问题Top
- 该阶段意图Top
- 该阶段情绪分布
- 代表触点列表
- 可追溯原文、来源渠道、时间、车型、门店

### 5.3 渠道 × 阶段矩阵

行是渠道，列是旅程阶段。

每个单元格展示：

- 触点数
- 负向占比
- Top问题

这个视图用于回答：“哪个渠道主要暴露哪个阶段的问题？”

### 5.4 业务动作建议

动作建议只基于规则，不做无数据支撑的AI生成。

示例规则：

- 报价/权益阶段价格问题高 -> 输出“销售话术/权益解释需优化”。
- 大众点评到店阶段负向高 -> 输出“门店接待/试驾体验需排查”。
- DCC战败原因集中在等优惠 -> 输出“跟进节奏与权益政策需复盘”。
- 公网对比评估阶段竞品配置讨论高 -> 输出“市场内容补充竞品对比素材”。

## 6. 数据模型设计

### 6.1 统一触点明细表

新增 `dwd_customer_touchpoint`。

| 字段 | 含义 |
| --- | --- |
| `touchpoint_id` | 触点ID |
| `source_channel` | 渠道：public_social、400、wecom、dcc、dianping |
| `source_system` | 具体来源系统或平台 |
| `source_record_id` | 原始记录ID |
| `channel_user_key` | 渠道内用户标识，可为昵称/脱敏ID/号码hash；不跨渠道打通 |
| `user_display_name` | 显示昵称，可脱敏 |
| `touchpoint_text` | 文本内容或摘要 |
| `touchpoint_time` | 触点时间 |
| `brand_name` | 品牌 |
| `model_name` | 车型 |
| `city_name` | 城市 |
| `store_id` | 门店ID，如有 |
| `store_name` | 门店名称，如有 |
| `event_id` | 关联事件，可为空 |
| `content_id` | 关联内容，可为空 |
| `journey_stage` | 旅程阶段 |
| `stage_confidence` | 阶段归因置信度 |

| `updated_time` | 更新时间 |

### 6.2 阶段汇总表

新增 `ads_journey_stage_summary`。

粒度：`brand_name + model_name + journey_stage + date_window`

指标：

- `touchpoint_cnt`
- `channel_cnt`
- `negative_touchpoint_cnt`
- `negative_ratio`
- `intent_top_json`
- `issue_top_json`
- `channel_distribution_json`
- `representative_touchpoints_json`

### 6.3 渠道阶段矩阵表

新增 `ads_journey_channel_matrix`。

粒度：`brand_name + model_name + source_channel + journey_stage + date_window`

指标：

- `touchpoint_cnt`
- `negative_ratio`
- `issue_top_json`
- `intent_top_json`

### 6.4 痛点汇总表

新增 `ads_journey_painpoint_summary`。

粒度：`brand_name + model_name + journey_stage + issue_tag`

指标：

- `touchpoint_cnt`
- `negative_ratio`
- `source_channels_json`
- `sample_texts_json`
- `suggested_owner`
- `suggested_action`

## 7. ETL设计

### 7.1 触点标准化

每个来源先进入统一触点表：

- 公网评论：从 `dwd_comment` 转为触点。
- 400：从来电摘要/工单文本转为触点。
- 企业微信：从会话摘要/跟进记录转为触点。
- DCC：从线索和外呼结果转为触点。
- 大众点评：从店铺评价转为触点。

### 7.2 阶段归因规则

归因优先级：

1. 业务字段优先：DCC阶段、外呼结果、门店评价、工单类型。
2. 文本标签其次：意图、问题、关键词、语义分类。
3. 渠道默认阶段兜底。

示例：

- DCC记录 `status=到店` -> 试驾/到店。
- 文本包含“报价、优惠、金融、置换” -> 报价/权益。
- 文本包含“已订、退订、买了竞品、等优惠” -> 下订/战败。
- 文本包含“售后、维修、保养、投诉、交付” -> 交付/售后。

### 7.3 汇总计算

首期只计算可被明细追溯的指标：

- 阶段触点数
- 阶段渠道分布
- 阶段负向占比
- 阶段Top问题/意图
- 渠道 × 阶段矩阵
- 代表触点
- 痛点建议规则

不计算：

- 跨阶段转化率
- 单用户路径
- 真实成交率
- 真实复购率

## 8. API设计

首期后端接口：

| API | 用途 |
| --- | --- |
| `GET /api/journey/overview` | 用户旅程总览 |
| `GET /api/journey/stages/{stage}` | 阶段详情 |
| `GET /api/journey/matrix` | 渠道 × 阶段矩阵 |
| `GET /api/journey/touchpoints` | 触点明细列表 |
| `GET /api/journey/painpoints` | 阶段痛点汇总 |

所有接口必须返回 `data_lineage` 字段，说明结果来自哪些表和哪些计算口径。

## 9. 前端设计

前端采用真实数据优先原则：

- API返回什么展示什么。
- API没有的字段不展示。
- 后端不可用时显示“未展示样例数据”，不使用mock填充。
- 页面上保留“数据来源/口径说明”。

页面结构：

1. 顶部筛选：品牌、车型、时间、渠道。
2. 旅程总览：九阶段横向卡片。
3. 渠道 × 阶段矩阵。
4. 阶段详情抽屉或详情页。
5. 触点证据列表。
6. 规则化业务动作建议。

## 10. 数据支撑分级

| 能力 | 首期处理 |
| --- | --- |
| 按渠道归因阶段 | 做 |
| 按阶段看痛点和意图 | 做 |
| 按阶段看代表原声 | 做 |
| 按渠道看阶段分布 | 做 |
| 单用户跨渠道路径 | 不做 |
| 转化率 | 不做 |
| 成交率/复购率 | 不做，除非接入订单和客户主数据 |
| AI自由摘要 | 不做，后续只基于真实聚合指标生成 |

## 11. 开发顺序

推荐严格按照以下顺序：

1. 数据模型：新增触点表和ADS汇总表。
2. 导入模板：增加 400、企微、DCC、大众点评触点模板。
3. ETL：实现触点标准化、阶段归因、阶段汇总、矩阵汇总、痛点汇总。
4. API：先输出真实数据接口。
5. 前端：只接真实API，不使用样例卡片。
6. 验证：用构造小样本验证每个阶段、每个渠道和每个汇总口径。

## 12. 首期成功标准

首期完成后，系统应该能回答：

- 当前品牌/车型在哪些用户旅程阶段声音最多？
- 每个阶段主要来自哪些渠道？
- 每个阶段用户的Top问题和Top意图是什么？
- 哪些阶段负向更高？
- 哪些触点可以回到原文证据？
- 哪些问题应该交给市场、销售、DCC、门店或售后处理？

同时系统必须明确不能回答：

- 某个真实用户是否从A渠道流转到B渠道。
- 某个用户是否真实成交。
- 某阶段到下一阶段的真实转化率。
- 真实复购率。
