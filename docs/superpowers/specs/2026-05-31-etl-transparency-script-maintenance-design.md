# 阶段1.5：ETL过程透明化与脚本维护设计

## 1. 目标

在「任务管理」中增加一层可理解、可维护的 ETL 管理能力，让使用者能看懂数据从上传到落库的过程，也让维护者能查看和修改当前 ETL 脚本。

第一版解决三件事：

1. 展示数据清理流程。
2. 展示每个流程节点的输入、输出、规则和脚本函数。
3. 支持查看、编辑、备份和试跑 ETL 脚本。

## 2. 页面范围

仍然放在一级菜单「任务管理」下，不新增一级菜单。

新增两个区域：

### 2.1 ETL清理流程

以流程节点展示：

1. 原始上传文件
2. ODS 原始层
3. 字段校验
4. 事件/内容/作者/评论标准化
5. REL 关系生成
6. ADS 指标聚合
7. PostgreSQL 落库

每个节点展示：

- 输入表
- 输出表
- 核心规则
- 对应脚本函数
- 当前选中批次的相关行数

### 2.2 脚本维护

第一版只维护一个脚本：

```text
etl/event_voc_ods_etl.py
```

功能：

- 查看脚本路径、更新时间、文件大小。
- 在线查看脚本内容。
- 编辑脚本内容。
- 保存前自动备份。
- 保存后可用当前选中批次试跑 ETL。

## 3. API

- `GET /api/etl/flow?batch_id=...`
  - 返回流程节点。
  - 如果传入批次，节点带上该批次的 summary 行数。

- `GET /api/etl/script`
  - 返回脚本路径、内容、更新时间、大小、最近备份。

- `PUT /api/etl/script`
  - 保存脚本内容。
  - 保存前备份旧文件到 `runtime/script_backups/`。

- `POST /api/etl/script/test-run`
  - 使用指定 `batch_id` 试跑当前脚本。
  - 返回新的 ETL summary 和错误信息。

## 4. 安全边界

第一版不做多人权限，但做最小保护：

- 只能编辑配置好的 ETL 脚本路径。
- 保存前必须自动备份。
- 不允许通过 API 传任意文件路径。
- 试跑只使用已有批次的 input 目录。

## 5. 不做事项

- 不做脚本审批流。
- 不做多人协同编辑。
- 不做语法高亮编辑器依赖。
- 不做任意脚本调度平台。
- 不做脚本版本 diff 页面；第一版只展示备份文件列表。

## 6. 验收标准

1. 页面能看到 ETL 流程节点。
2. 选中批次后，流程节点能显示相关行数。
3. 页面能查看当前 ETL 脚本内容。
4. 保存脚本时会生成备份。
5. 保存后能用选中批次试跑。
6. 全量测试通过，服务正常启动。
