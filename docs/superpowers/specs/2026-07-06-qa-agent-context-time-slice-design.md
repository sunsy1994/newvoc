# QA Agent 连续对话与时间切片设计

## 目标

补齐 QA Agent 的两个能力缺口：连续追问必须使用有限历史上下文；用户指定日期时，统计值与证据必须来自该日期范围，而不是只在答案尾部展示时间标签。

## 范围

- 保持现有三个看板接口和默认查询行为不变。
- 只在 `app/agents/qa` 内新增 Agent 专用时间切片查询。
- 保持现有五个 Tool 名称和最多三轮 ReAct 流程不变。
- 不新增通用 SQL Agent，不允许模型生成 SQL。

## 连续对话

`history` 只保留最近六条有效消息，每条只接受 `user` 或 `assistant` 角色，并限制文本长度。决策器与修订器都接收格式化历史，但提示词明确规定：

1. 历史用于理解“它、这个事件、价格呢”等指代和追问关系。
2. 历史 Assistant 回答不是事实来源；当前 Tool observation 与当前时间范围优先。
3. 当前问题明确给出的事件或时间覆盖历史语境。
4. 没有足够信息解析事件时继续走澄清节点，不能猜测。

## Agent 专用时间切片

新增轻量查询模块 `app/agents/qa/time_slice.py`，由现有 QA Tools 调用。它直接读取现有 `data_asset` 内容与评论资产，但查询模板固定、参数化，不暴露给模型。

时间口径：

- 市场内容指标以 `dwd_content.published_at` 为准。
- 产品、销售和评论证据以 `dwd_comment.published_at` 为准，并通过内容表限定 `event_id`。
- 日期使用闭区间；SQL 上界使用“结束日期次日零点”以覆盖结束日全天。
- 事件列表继续按事件周期与查询范围是否相交过滤。

各 Tool 返回最小但可回答的数据：

- `get_market_story`：内容数、评论数、互动量、按日趋势、平台分布、区间热门内容。
- `get_product_story`：关注点提及量、正负向数量、购买信号数量及区间代表评论。
- `get_sales_story`：购买信号分布、线索数量、平台来源及区间代表评论。
- `get_discussion_evidence`：指定关注点在区间内的原始评论和总数。

当时间模式为 `event_period` 时仍可复用现有看板聚合，避免重复查询；当模式为 `explicit` 或 `default_30_days` 时使用时间切片层，保证跨事件和显式日期口径真实。若 Tool 已锁定具体事件，默认近 30 天也按同一切片规则执行。

## 数据流

1. `initialize` 规范化历史、解析事件和时间范围。
2. `decide` 结合当前问题、有限历史、草稿和 observations 选择一个 Tool。
3. QA Tool 根据时间模式选择现有看板聚合或时间切片查询。
4. `revise` 只依据当前 observations 修订草稿，历史只帮助理解追问。
5. 最多三轮后 `finalize` 输出答案、事件、真实统计区间和数据口径。

## 错误处理

- 日期格式非法或开始日晚于结束日时返回明确错误。
- 未找到事件时进入澄清，不猜测事件。
- 时间范围内没有数据时返回零统计和空证据，由修订器明确说明“该区间暂无数据”。
- Tool 名称仍受白名单约束。

## 验证标准

- Prompt 测试证明最近历史被包含，过旧历史被截断，且包含“历史回答不是事实”的约束。
- Tool 测试证明显式日期会传入时间切片层，而事件完整周期仍复用现有看板。
- SQL 单元测试证明开始日和结束日进入参数，结束日按次日零点形成半开区间。
- Agent 测试证明“那价格呢？”可携带上一轮上下文进入决策和修订。
- 原 QA Agent、Dispatcher、问数 Agent 和前端架构测试继续通过。
