# AutoVOC 证据驱动洞察推演 Agent 设计

## 目标

把现有 AI 洞察入口建设为独立的“用户反应推演 Agent”。用户输入一个尚未发生或准备实施的企业动作，例如车型减配、调价或新车上市，Agent 从已入库的历史事件中检索相似案例，只依据真实事件指标和评论证据推演用户可能的反应。

核心原则是：没有证据就不推演；证据只能支持到哪里，结论就写到哪里。

第一版只在 AI 对话中展示结果，不保存为资产，不新增数据库表，也不预测销量、声量或用户反应的精确百分比。

## 能力边界

- 洞察由现有统一 Agent API 的 `insight` 能力硬路由到独立 Agent。
- 洞察不复用问数、问答或报告的 Graph、提示词与业务输出结构。
- Agent 可以跨品牌检索相似事件，优先级为同车型、同品牌、跨品牌竞品。
- 跨品牌证据必须在结果中明确标注，不能包装成同车型或同品牌事实。
- 第一版支持配置调整、价格权益和新品上市等事件推演，其中优先跑通“减配或调价”场景。
- Agent 不提供产品、营销或销售行动建议，只描述证据支持的潜在用户反应和影响方向。
- Agent 不使用模型常识补齐事件库缺失的信息。

## 用户输入与场景解析

Agent 首先把用户自然语言解析成结构化场景：

```json
{
  "action_type": "配置减少",
  "affected_aspects": ["座椅通风"],
  "compensation": ["价格降低1万元"],
  "target": "新款车型",
  "expected_scope": "上市后用户反应"
}
```

关键场景字段缺失时不进入推演。例如用户只说“准备减配”，但没有说明减配对象，Agent 返回澄清问题。用户在后续对话中补充或限定条件时，可以继承上一轮场景，但必须重新检索并校验证据，不能把上一轮生成的结论当作事实。

## 相似事件检索

第一版采用“规则召回 + LLM 重排”，不引入向量数据库。

### 规则召回

后端使用现有事件与看板服务，按以下信息召回最多 10 个候选事件：

- 事件类型与事件名称；
- 品牌与车型；
- 产品关注点；
- 场景关键词和评论关键词；
- 情绪与购买信号数据是否可用。

候选排序优先级为：同车型、同品牌、跨品牌竞品。

### LLM 重排

LLM 只判断候选事件与目标场景的相关性，包括：

- 相似的企业动作和产品关注点；
- 可用于推演的真实证据；
- 目标场景与历史事件之间的关键差异；
- 同车型、同品牌或跨品牌关系。

LLM 将候选事件划分为强相似、中等相似或不相关，最多保留 3 至 5 个相似事件。重排阶段不生成用户反应结论。

## 证据门槛与停止规则

停止规则由后端程序执行，不能只依靠提示词：

- 没有候选事件时，返回 `insufficient_data`。
- 没有至少 1 个强相似事件，且中等相似事件少于 2 个时，停止完整推演。
- 相关真实评论总数少于 10 条时，停止完整推演。
- 只有部分场景证据时返回 `partial`，只展示相似事件、已知信息和数据缺口，不生成完整用户反应判断。
- 场景缺少关键条件时返回 `needs_clarification`。
- 只有满足全部证据门槛时才返回 `completed`。

当事件库不满足门槛时，面向用户明确显示：

> 暂无此类数据推演。当前事件库未找到足够相似的历史事件，或相关评论证据未达到推演门槛。

状态值固定为：

- `completed`：证据达到门槛，生成完整推演；
- `partial`：存在部分匹配，只展示证据和边界；
- `insufficient_data`：无足够数据，不生成推演；
- `needs_clarification`：需要用户补充场景条件。

## LangGraph 架构

新增独立的 `app/agents/insight/` 包，并将 Runner 注册到现有 Dispatcher 的 `insight` 能力。

Graph 使用固定执行路径，不建立开放式无限 ReAct：

```text
场景解析与检索
  -> 证据门槛判断
  -> 用户反应推演
  -> 证据一致性复核与一次修正
  -> 结构化结果
```

节点数量不等于模型轮次。最多执行三轮模型工作：场景解析与相关性判断、证据推演、证据复核与一次修正。规则召回和证据门槛判断由后端代码执行，不占用模型推理轮次。复核仍不通过时，删除无证据结论或降低为 `partial`，不能继续循环。

## Tools

第一版提供三个职责清晰的工具，工具包装现有事件与看板服务，不复制 SQL：

### `list_candidate_events`

根据结构化场景召回候选事件，返回事件名称、事件类型、品牌、车型、时间和关系类型。

### `get_event_reaction_evidence`

获取候选事件的产品关注点、情绪、购买信号、用户群、相关评论和数据时间范围。真实评论保留事件、平台和时间来源。

### `compare_event_similarity`

整理目标场景与候选事件之间的相似点、关键差异及同车型、同品牌、跨品牌关系，为重排和证据门槛提供标准输入。

## 推演规则

完整推演只输出以下内容：

- 支持、观望、反对三类可能反应；
- 受影响的真实可识别用户群；
- 可能被放大的产品关注点；
- 口碑、购买信号和传播风险的方向；
- Agent 归纳的表达主题；
- 历史事件中的真实评论原话；
- 相似事件、置信度和数据边界。

第一版仅使用“主要、次要、证据不足”等定性强度，不生成无法校验的反应百分比。没有用户画像证据的人群不展示。每项主要判断必须关联至少一个历史事件和一组支持证据。

“可能出现的表达主题”和“真实证据原话”必须分开显示。Agent 不得生成伪装成真实用户原话的句子。

## 提示词约束

洞察 Agent 的系统提示词必须明确：

- 只能使用 Tools 返回的数据和证据；
- 每个主要判断必须关联事件与证据；
- 不得使用模型常识补充用户反应；
- 不得伪造评论原话或证据来源；
- 不得生成无依据的百分比；
- 跨品牌证据必须明确标注；
- 相关性或评论数量不足时必须拒绝完整推演；
- 使用“可能、倾向、证据显示”等概率表达，不使用“必然、一定”；
- 不输出产品、营销或销售建议；
- 必须返回约定的结构化 JSON。

## 输出结构

后端返回独立的 `InsightResult`，不复用报告业务结构：

```text
status
scenario
confidence
data_scope
reaction_cards
audience_cards
impact_cards
expression_themes
evidence_comments
similar_events
limitations
```

前端依据 `status` 选择完整推演卡片、部分匹配卡片、数据不足状态卡或澄清问题。

## 对话卡片

洞察结果只在 AI 对话消息中展示。视觉上复用报告的卡片容器、标题层级、色块、间距和证据展开交互，但使用独立的 `InsightResultCard` 和数据类型。

完整结果固定为五组卡片：

1. 用户反应判断：支持、观望、反对；
2. 受影响用户群：可能反应、主要关注点和判断依据；
3. 口碑与购买信号：口碑方向、产品关注点、购买信号和传播风险；
4. 表达主题与真实证据：归纳主题和可展开的真实评论；
5. 相似事件与推演边界：关系类型、相似点、差异、评论数量和不能覆盖的范围。

`insufficient_data` 不渲染空的完整卡片，只显示一张明确说明已检索范围和数据缺口的状态卡。洞察结果不提供“查看报告”按钮，不写入报告资产，也不出现在资产库。

## 错误与降级

- LLM 场景解析失败时返回可理解的澄清提示，不执行事件检索。
- 单个候选事件数据读取失败时跳过该事件，并在数据边界中说明；全部失败时返回 `insufficient_data`。
- LLM 重排或推演调用失败时沿用统一 Agent API 的错误处理与错误记录机制。
- 证据复核发现结论缺少来源时，最多修正一次；修正后仍无依据则删除结论或返回 `partial`。
- 普通问数、问答和报告能力的路由与返回结构保持不变。

## 验收标准

- 存在 1 个强相似事件且相关评论不少于 10 条时，可以生成完整卡片。
- 存在至少 2 个中等相似事件且相关评论不少于 10 条时，可以生成完整卡片。
- 没有相似事件时明确返回“暂无此类数据推演”，且不进入结论生成。
- 评论不足时返回 `insufficient_data`。
- 部分匹配时返回 `partial`，不生成完整反应判断。
- 跨品牌证据在事件卡和结论依据中正确标注。
- 结果不包含伪造评论、无依据百分比或行动建议。
- 对话追问可以继承场景条件，但会重新获取并校验证据。
- 洞察只在 AI 对话中展示，不写入报告资产或其他资产库表。
- 问数、问答和报告 Agent 的现有路由与行为不受影响。

## 非目标

- 不建立向量数据库或新的事件标签系统；
- 不训练预测模型；
- 不预测销量、声量或精确反应比例；
- 不保存洞察资产；
- 不生成产品或营销建议；
- 不自动把推演结果回写为事实数据。
