# 销售部 AI 报告线索复盘设计

## 目标与定位

销售部 AI 报告定位为事件结束后的销售线索复盘，核心回答四个问题：产生了多少可用线索、用户正在表达什么需求、哪些内容带来了线索、哪些对象值得进入承接池。

报告只使用销售看板现有结构化数据。LLM 生成复盘文案，系统固定指标、图表和排序。报告不生成营销承诺，不补造联系方式或用户身份，不把“建议联系用户”表述为已经完成跟进。

## 故事线

### 顶部结论

用一句标题和一段摘要概括线索产出质量、主要需求、核心来源与承接规模。摘要按“产出—需求—来源—对象”组织，不逐项复述章节文字。

### 第一章：线索产出

回答本次事件从已打标评论中沉淀了多少车相关反馈、销售意图和中/强购买信号。

- 核心数据：`lead_quality.summary`
- 固定阶段：已打标评论 → 车相关评论 → 销售相关意图 → 中/强购买信号
- 辅助指标：强购买信号数量和占比

### 第二章：用户需求

回答用户主要表达购买意向、配置咨询、询价、价格敏感、竞品对比或其他意图，以及这些需求对应的购买信号强度。

- 意图数据：`lead_quality.intent_distribution`
- 信号数据：`lead_quality.purchase_signal_distribution`
- “无效”“玩梗”等非销售意图保留真实数量，但在视觉上作为非机会项弱化，不从数据中删除。

### 第三章：线索来源

回答哪些具体内容带来了中高意向和强购买信号。平台只作为内容来源标签；当存在多个平台时，平台效率作为辅助证据，不单独占据固定章节。

- 来源汇总：`lead_source.summary`
- 内容明细：`lead_source.content_leads`
- 平台辅助：`lead_source.platform_efficiency`
- 线索评论：`lead_source.lead_comments`

### 第四章：承接对象

回答强信号与中信号用户分别形成了多大承接池，用户已维护的画像标签是什么，代表性原话如何支撑信号判断。

- 用户分层：`lead_quality.profile_segments`
- 承接列表：`recommended_follow_up_users`
- 证据评论：`lead_quality.evidence_comments`
- 未维护画像必须明确显示为“未画像用户”，不得由 LLM 推断画像。

## 摘要模式

摘要模式复用产品部和市场部共享故事线外壳与单一主题色体系：

1. 顶部展示事件名、核心判断和最多三个真实指标。
2. 纵向展示“线索产出—用户需求—线索来源—承接对象”四章。
3. 每章只展示一个主结论、两至三个关键指标和一段解释。
4. 代表评论及用户明细默认折叠，用户主动展开后查看。
5. 数据缺失时保留章节位置并展示明确空状态，不让 LLM 补齐。

## 图表模式

说明文字统一位于图表上方。四种图表由系统固定，LLM 不选择模板或数据点。

### 线索产出：阶段转化漏斗

- 阶段顺序固定为已打标、车相关、销售意图、中/强信号。
- 每一级展示数量及相对上一级转化率。
- 强购买信号作为漏斗下方的辅助指标，不增加第五阶段。
- 任一后续阶段大于前序阶段时视为非法数据，整张图进入空状态。

### 用户需求：横向意图排名图

- Y 轴：意图类型，最多展示前 8 项。
- 条形长度：评论数。
- 标签：评论占比。
- 机会意图使用主题色；“无效”“玩梗”等非机会项使用低透明度同色，不引入额外警示色。
- 购买信号分布以同一卡片下方的连续分段条展示，作为意图结构的补充。

### 线索来源：内容线索贡献图

- 每行代表一条内容，最多展示前 8 条。
- 主长度：中/强意向评论数 `high_intent_comment_count`。
- 内部深色段：强信号评论数 `strong_signal_comment_count`。
- 辅助标签：总评论数、平台、作者。
- 排序固定为中/强意向数降序、强信号数降序、总评论数降序。
- 没有内容级来源时，降级展示平台级线索效率；不得制造内容归因。

### 承接对象：用户信号梯队

- 第一列：强购买信号用户。
- 第二列：中购买信号用户。
- 每列展示用户数、已维护画像标签分布和最多 5 个代表用户。
- 单个用户展示昵称、平台、画像状态和代表评论；不展示系统未提供的个人信息。
- 同一用户只出现一次，优先归入其最高购买信号梯队。
- 没有用户明细但有汇总数量时，只展示梯队数量，不生成虚拟用户。

## 数据与生成边界

销售 Prompt 固定输出标题、摘要、四章故事线、四张图对应的章节解读和数据说明。所有指标引用只能来自销售上下文中的已知路径，评论证据引用只能使用上下文中真实存在的评论或用户标识。

LLM 不得：

- 生成图表、排序或计算结果；
- 补造手机号、微信、真实身份、年龄、性别、收入或所在地；
- 将购买信号解释为已经成交；
- 输出折扣承诺、价格承诺或联系结果；
- 为未维护画像的用户推断画像；
- 根据一条评论扩展出系统没有提供的用户事实。

## 隐私与展示边界

- 只展示接口已有昵称、平台、画像状态、信号等级和代表评论。
- `comment_user_id` 只用于系统内去重和引用，不在卡片主视觉中展示。
- 代表评论保持原文，但继续遵守系统已有内容脱敏规则。
- 承接对象仅表示数据分层结果，不自动触发消息、外呼或导出。

## 兼容与错误处理

- 历史销售报告继续按旧图表和旧摘要读取，不在查询时迁移。
- 新报告只有在故事线章节与新图表契约同时匹配时启用新版摘要。
- 前端归一化必须同时识别产品、市场和销售三种故事线，不能使用单一部门校验器过滤其他部门。
- 四张新图均必须使用共享图表外壳，保留标题、上方解读、来源和空状态。
- 单章数据缺失不影响其他章节；整份报告无可渲染数据时使用现有空报告状态。

## 验收标准

1. 摘要模式呈现一段顶部结论与四章销售故事线，不再复述图表说明。
2. 图表模式依次展示线索漏斗、用户需求、内容来源、用户信号梯队。
3. 原“渠道线索效率”被内容线索贡献替代；多平台数据只作为辅助或降级展示。
4. 图表标题、说明文字、数据来源和空状态均正常显示。
5. 未维护画像不被推断；没有用户明细时不生成虚拟用户。
6. 最新销售报告能被前端保留和识别，不回退旧摘要。
7. 历史销售报告、产品报告、市场报告和事件综合报告继续正常展示。
8. 后端全量测试、前端类型检查和生产构建通过。

## 明确不在本轮范围内

- 新增用户联系方式或 CRM 字段；
- 自动外呼、私信、派单或导出；
- 新增数据库业务指标；
- 实时销售告警；
- LLM 动态选择图表；
- 修改产品部、市场部及事件综合报告的业务故事线。
