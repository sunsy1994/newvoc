# 三部门 AI 总结“数据依据”设计

## 目标

将市场部、产品部、销售部 AI 总结中的“数据依据”从开发调试信息改为业务可读、可追溯的数据口径说明。用户应能直接回答：报告用了什么数据、数据来自哪里、如何处理、支撑哪项判断，以及数据是否存在缺失。

## 范围

- 修改市场部、产品部、销售部 AI 总结弹窗的“数据依据”模式。
- 保留现有摘要模式、图表模式、报告故事线和图表合同。
- 不增加数据库表，不接入新的外部数据，不改变现有指标计算逻辑。
- Prompt 与完整结构化输入保留为底部折叠的“技术详情”，不再作为业务数据依据的主体。

## 设计原则

1. 数据依据由系统根据固定合同生成，不交给 LLM 自由编写。
2. 只展示当前报告实际使用的现有接口数据和现有计算逻辑。
3. 明确区分四种生产方式：直接统计、规则计算、LLM 标签、LLM 总结。
4. 计算口径必须来自系统固定定义；输入缺失时显示“本次未提供”，不得推断或补造。
5. 数据依据按报告故事线章节组织，使依据与摘要、图表一一对应。

## 统一数据结构

每个部门报告返回 `data_basis`，包含报告范围和四个章节依据：

```json
{
  "scope": {
    "event_name": "",
    "start_time": "",
    "end_time": "",
    "generated_at": ""
  },
  "sections": [
    {
      "chapter_id": "",
      "title": "",
      "data_items": [""],
      "sources": [""],
      "processing_steps": [
        {"type": "direct|rule|llm_label|llm_summary", "description": ""}
      ],
      "metric_definitions": [""],
      "supports": "",
      "availability_note": ""
    }
  ]
}
```

`data_basis` 由后端使用本次报告的 `context`、固定图表合同和固定口径字典生成。前端只负责通用渲染，不自行解释业务公式。

## 市场部数据依据

### 传播结果与节奏

- 使用数据：内容发布日期、评论日期、内容数、评论数、互动量、日趋势。
- 数据来源：当前事件关联的内容库、评论库及事件趋势聚合结果。
- 处理方式：按日期直接聚合内容与评论；互动量使用现有互动字段累计；峰值和阶段判断使用现有规则结果；LLM 仅负责解释既有指标。
- 支撑内容：传播规模、峰值日期、传播阶段和节奏结论。

### 话题驱动

- 使用数据：内容标题或正文中的话题、话题关联内容数、评论数、互动量。
- 数据来源：当前事件关联内容及其评论。
- 处理方式：话题由现有规则抽取；内容、评论和互动按话题聚合；LLM 解释主要话题的传播作用。
- 支撑内容：主要话题、话题热度及传播贡献。

### 传播主体

- 使用数据：作者、KOL、发布内容数、评论量、互动量。
- 数据来源：作者库、KOL 画像与事件内容关联结果。
- 处理方式：按主体聚合现有内容和互动数据；主体身份沿用系统已有标签；LLM 解释主体贡献。
- 支撑内容：主要传播者、主体结构和贡献差异。

### 渠道效率

- 使用数据：平台、内容数、评论数、互动量及现有平台效率指标。
- 数据来源：事件内容和评论的平台字段。
- 处理方式：按平台直接聚合；效率使用系统已有计算口径；LLM 解释渠道差异。
- 支撑内容：主要渠道、渠道覆盖与效率判断。

## 产品部数据依据

### 用户关注

- 使用数据：产品点、提及次数、提及占比、关联评论。
- 数据来源：当前事件评论及现有产品点标签。
- 处理方式：产品点属于 LLM 标签结果；提及次数与占比由系统统计；LLM 总结用户关注结构。
- 支撑内容：用户主要关注的产品维度。

### 评价态度

- 使用数据：产品点正向、中性、负向评论数及比例。
- 数据来源：评论库中的产品点和情感标签。
- 处理方式：产品点与情感属于 LLM 标签；数量和比例由系统计算；LLM 解释评价结构。
- 支撑内容：各产品点的认可、争议和负面反馈。

### 竞品比较

- 使用数据：对比车系、对比维度、比较方向、评论次数。
- 数据来源：评论库中的 PKO 关系标签和关联事件车型信息。
- 处理方式：PKO 对象、维度和方向属于 LLM 标签；次数及占比由系统统计；LLM 解释比较关系。
- 支撑内容：用户在和谁比较、比较什么、结果如何。

### 证据支撑

- 使用数据：真实评论、评论标识、产品点或 PKO 标签。
- 数据来源：当前事件关联评论。
- 处理方式：系统按现有排序与筛选规则选择证据；LLM 只能引用输入中的真实评论标识。
- 支撑内容：为产品机会点、风险点、惊喜点及比较结论提供可追溯证据。

## 销售部数据依据

### 线索产出

- 使用数据：已打标评论、车相关评论、销售意图评论、中/强购买信号。
- 数据来源：当前事件评论及现有销售标签。
- 处理方式：车相关、销售意图、购买信号属于 LLM 标签；各阶段数量与转化比例由系统计算。
- 支撑内容：线索规模、线索质量和漏斗结果。

### 用户需求

- 使用数据：销售意图分布、购买信号分布及对应评论数。
- 数据来源：评论库中的销售意图和购买信号标签。
- 处理方式：标签由 LLM 产生；数量与比例由系统统计；LLM 解释需求结构。
- 支撑内容：用户询价、优惠、配置、购买等需求重点。

### 线索来源

- 使用数据：内容、作者、平台、评论数、高意向评论数、强购买信号数。
- 数据来源：事件内容、作者信息及关联评论。
- 处理方式：按内容与平台聚合销售标签；系统计算线索贡献；LLM 解释主要来源。
- 支撑内容：哪些内容和渠道带来了销售线索。

### 承接对象

- 使用数据：真实用户标识、昵称、平台、购买信号、画像标签和代表评论。
- 数据来源：评论用户库、用户画像及关联评论。
- 处理方式：按强、中购买信号分组并去重；画像和销售标签沿用现有结果；不生成成交判断或营销承诺。
- 支撑内容：当前数据中可进一步关注的用户梯队及其公开表达。

## 前端呈现

“数据依据”模式顶部展示本次报告范围：事件名称、数据起止时间和报告生成时间。下方按故事线顺序展示四张依据卡。

每张卡包含：

- 使用数据
- 数据来源
- 处理过程（使用四类标识）
- 指标口径
- 支撑结论
- 数据完整性说明

默认不显示内部字段路径、数据库表名、Prompt 和 JSON。弹窗底部保留折叠的“技术详情”，其中展示完整 Prompt 和结构化输入，供开发排查使用。

## 缺失与兼容处理

- 新生成报告保存完整 `data_basis`。
- 历史报告没有 `data_basis` 时，前端可根据其合法 `context` 和图表合同使用同一固定构建逻辑补齐；无法识别的部分显示“历史报告未记录该项依据”。
- 单个章节无数据时仍展示章节，并明确说明“本次未提供相关数据”，不隐藏章节。
- 旧版 Markdown 报告继续按原方式展示，不伪造新的数据依据。

## 测试与验收

1. 三部门新报告均返回四个、顺序固定的数据依据章节。
2. 每个章节包含数据、来源、处理方式、口径、支撑内容和完整性说明。
3. 处理方式能正确区分直接统计、规则计算、LLM 标签和 LLM 总结。
4. 页面不再以 Prompt 或 JSON 作为“数据依据”主体。
5. Prompt 与 JSON 仍可在折叠的“技术详情”中查看。
6. 空数据和历史缓存均不报错、不补造数据。
7. 摘要模式、图表模式及既有市场、产品、销售图表不发生回归。
